# Комментарии в коде

Читатель комментария — человек, который откроет файл через год. У него нет ни MR, ни Jira,
ни разговора, в котором писался код. Есть только код и `git blame`.

## Когда комментарий нужен

Пишу комментарий, только если без него читатель не поймёт того, чего в коде не видно:

- почему код написан так, а не очевидным способом; какой более простой вариант не подошёл и чем;
- внешнее ограничение: поведение чужого API, ошибка библиотеки или платформы (со ссылкой на
  issue upstream), требование протокола или закона;
- инвариант, порядок вызовов, предусловие, которое код сам не проверяет;
- единицы измерения, допустимые границы, смысл значения, которое нельзя вынести в
  именованную константу;
- последствие, которого не видно из строки: блокировка таблицы, внешний вызов, необратимость;
- контракт публичного метода: что принимает и что гарантирует, а не как устроен внутри.

## Чего в комментарии быть не должно

- Пересказа кода: `# increment counter`, `# call the service`.
- Истории изменения: «добавил», «теперь», «раньше», «больше не», «в этом MR», «после
  рефакторинга». Историю хранит git.
- Номера задачи как ответа на вопрос «откуда этот код», дат, имён авторов, «как договорились».
- Замеров и статистики: «быстрее на 30%», «за 14 дней 0 совпадений». Их место — описание MR и Jira.
- Состояния чужих систем, которое меняется без правки этого файла: «у сервиса X не настроены
  оповещения», «на проде сейчас 3 пода».
- Закомментированного кода.
- Меток без причины: `# hack`, `# не трогать`.

Если комментарий объясняет, *что* делает код, сначала переименовать переменную или метод,
вынести метод или константу. Комментарий в этом случае не нужен.

## Исключения

- `TODO`/`FIXME` с ключом задачи и условием удаления:
  `# TODO(PROJ-123): remove together with the foo_bar feature flag`. Задача живёт дольше MR, и
  ключ ведёт к незакрытой работе. TODO без ключа или без условия не пишу.
- Ссылки на постоянные документы: issue upstream, RFC, спецификацию API, tech-design.
- Правила репозитория важнее этого файла: если они требуют комментарий определённого вида
  (например, описать последствие миграции или сослаться на задачу), пишу его.

## Два теста для каждого комментария

1. Потеряет ли читатель через год что-то, если комментарий удалить? Нет — удалить.
2. Станет ли комментарий ложным, если изменится что-то вне этого файла или просто пройдёт
   время? Да — переписать, чтобы не стал, или перенести в описание MR.

## Когда меняю код

Комментарии рядом с изменённым кодом перечитываю: устаревший комментарий хуже отсутствующего.
Обновляю или удаляю его в том же коммите. Язык комментария — как в окружающем коде.

## Проверка перед MR

`~/.claude/bin/review branch` сначала запускает `~/.claude/bin/comment-check`: отдельный
`claude -p` без контекста задачи читает комментарии ветки по этому файлу. Если он вернул правки
для автора (`review` выходит с кодом 6), вношу их новым коммитом и запускаю ревью снова. Вопросы
к пользователю попадают в описание ревью (info popup revdiff) и в вывод `review`. Текст, который проверка велела перенести
в MR, она дописывает в файл `mr-notes.md` и печатает путь к нему; при описании MR беру его оттуда.
